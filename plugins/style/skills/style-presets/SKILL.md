# Style presets reference

The `style` plugin ships rule blocks that govern **how information is
communicated**: tone, terminology, phrasing, and the shape output takes. It
does not govern code style (that is the linter's job) or visual design (that is
`designer@magus`).

`/style:apply` composes the chosen rules into a single **native Claude Code
output style** and activates it. All file work is done by
`scripts/compose-style.ts`, which is tested; the commands only decide what goes
in the set.

## The axis model

Presets sit on one of two axes, and the axis decides how they combine.

| Axis | Rule | Presets |
|---|---|---|
| `verbosity` | pick **exactly one** — they contradict each other | `direct`, `explanatory`, `terse` |
| `modifier` | combine freely | `evidence-first`, `plain-language`, `no-slop`, `structured`, `calibrated`, `terminology` |

The one-verbosity rule is not a style preference. `terse` says "do not explain
unless asked" and `explanatory` says "explain the specific choice"; applied
together they cancel, and the model resolves the contradiction unpredictably
turn to turn. One wins by being the only one present.

`plain-language` lists `terse` as a conflict for the same reason: glossing
jargon on first use costs words that `terse` forbids. The other modifiers are
orthogonal and stack cleanly.

## What each preset governs

| Preset | Governs |
|---|---|
| `direct` | Answer position, no preamble/postamble, recommend over survey |
| `explanatory` | Reasoning after the conclusion, rejected alternatives, mechanism claims |
| `terse` | Word count, fragments over sentences, no unrequested explanation |
| `evidence-first` | Commands and real output behind every claim; negative controls |
| `plain-language` | Jargon glosses, concrete nouns, active voice, reader impact |
| `no-slop` | Banned vocabulary, banned connectives, em dashes, formatting tics |
| `structured` | Table vs list vs paragraph, headings, backticks, `file:line` |
| `calibrated` | Confidence matching evidence, "I don't know", correction discipline |
| `terminology` | One name per concept; `template: true`, filled from the codebase |

## How composition works

Claude Code activates **exactly one** output style at a time — its resolver
returns a single object. That is the whole reason this plugin composes: nine
composable presets cannot be nine output styles, or picking two would be
impossible.

`/style:apply` writes one generated file and points the setting at it:

```
.claude/output-styles/composed.md     the composed rules
.claude/settings.json                 "outputStyle": "composed"
```

with `--global` writing to `~/.claude/` instead. The generated file opens with:

```markdown
---
name: composed
description: "Composed communication style: direct, no-slop"
keep-coding-instructions: true
---

<!-- Generated by /style:apply. Re-run it to change this file; hand edits are lost. -->
<!-- style:presets: direct, no-slop -->
<!-- style:imports: user:my-voice -->
```

The two provenance comments are the record of what went in. `/style:list`
reads them. Do not edit them by hand — the next run overwrites the file
wholesale.

**Ordering is imports, then verbosity, then modifiers.** An imported style is a
whole personality; a preset is a specific, checkable rule. Specific-after-broad
means a preset rule refines an imported one rather than being buried by it.

## What the harness does with it

The body is injected into the system prompt as:

```
# Output Style: composed
<body>
```

and the opening identity line changes from "You are an interactive agent that
helps users **with software engineering tasks**" to "…**according to your
'Output Style' below, which describes how you should respond to user
queries**." That is the real difference from CLAUDE.md, and it is not about
token count: CLAUDE.md is project context the model is told to follow, while an
output style is part of what the model is told it *is*.

Two frontmatter flags decide the rest, and both matter:

| Flag | Effect |
|---|---|
| `keep-coding-instructions: true` | **Mandatory here.** Without it, Claude Code drops its own coding-discipline block — no premature abstraction, no error handling for impossible cases, default to no comments, verify UI changes in a browser. All three built-in styles set it. A plugin about communication must not switch off how code gets written. |
| `force-for-plugin: true` | **Never use.** A plugin shipping this overrides the user's `/output-style` choice outright, and two plugins forcing means one silently loses with a warning. |

## Importable styles, and the one thing that cannot be imported

`compose-style.ts` discovers styles the user already has:

| Scope | Directory | Selector |
|---|---|---|
| user | `~/.claude/output-styles/*.md` | `user:<name>` |
| project | `<project>/.claude/output-styles/*.md` | `project:<name>` |

The generated file excludes itself, or each run would fold the previous run's
output back in and grow without bound.

## Built-in styles

`Explanatory`, `Learning`, and `Proactive` ship inside the Claude Code binary
rather than on disk, so there is no file for `compose-style.ts` to read.
Composing *replaces* whichever style was active, built-in included, and
`/style:apply` says so in its report.

**They are capturable, on the user's own machine.** `scripts/capture-builtin.ts`
does it:

```bash
bun ${CLAUDE_PLUGIN_ROOT}/scripts/capture-builtin.ts --discover  # names shipped today
bun ${CLAUDE_PLUGIN_ROOT}/scripts/capture-builtin.ts --all       # capture every one
bun ${CLAUDE_PLUGIN_ROOT}/scripts/capture-builtin.ts --check     # what fell behind
```

It writes `~/.claude/output-styles/builtin-<name>.md`, which then imports as
`user:builtin-<name>` like any other style.

The method is a transparent proxy in front of the Anthropic API plus one
`claude -p` round trip with the style active, recording the `system` field of
the request. Grepping the binary is *not* used for the text: the registry
symbol is minified and changes every release, so the grep breaks silently.
Names are read that way, since a wrong name is cheap to spot and the text is
not.

**Captures are never committed here.** They are Anthropic's prompt text, and
they go stale on Anthropic's release schedule rather than ours. Per machine
means nothing is redistributed and the text matches the binary installed.

Each file records `captured-from: <version>`. Run `--check` after every Claude
Code upgrade: it exits non-zero on stale captures and lists built-ins that
exist but were never captured, which is how a newly introduced style surfaces.

Full method, the failure modes, and how to verify a capture is complete:
`ai-docs/claude-code-builtin-output-style-extraction.md`.

## Templates

A preset with `template: true` ships a structure that is worthless until it is
filled from the actual codebase. `terminology` is the only one.

The script **refuses** it as a preset, because a preset body is copied
verbatim and would land as an empty table. `/style:apply` fills it in, writes
it to `.claude/output-styles/terminology.md`, and passes it as
`--import project:terminology`. The filled result is then a real file the user
can read, edit, and commit.

## Cost

An output style is in every request's prompt, same as CLAUDE.md. A preset that
reads well and changes nothing is pure overhead. Each preset is deliberately
short, and `/style:apply` reports the generated file's line and byte count for
the same reason. If a project applies all nine, that is the point at which to
ask which ones actually altered anything.

## Adding a preset

Drop a file in `${CLAUDE_PLUGIN_ROOT}/styles/<name>.md`:

```markdown
---
name: <kebab-case, matching the filename>
axis: verbosity | modifier
summary: <one line — becomes the option description in /style:apply>
conflicts: <comma-separated preset names, or empty>
template: true   # optional — only if the body needs filling from the codebase
---

### <Title Case heading>

- <rules>
```

The body is copied verbatim into the composed style, so write it as the rules
themselves, not as documentation about the rules. It must open with a `###`
heading so it nests under the composed file's `##`.

Both commands discover presets by globbing the directory. Nothing is
registered, and no manifest lists them — a new file is available immediately,
and `scripts/compose-style.test.ts` reads the real directory rather than a
fixture, so a malformed preset fails the suite.

Write rules that are checkable. "Be clear" cannot be followed or violated;
"no em dashes" and "cite the command that produced the output" can.
